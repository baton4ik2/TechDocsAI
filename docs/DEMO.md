# TechDocs AI — разбор по разделам

Технический разбор приложения для показа: что делает каждый раздел и как он
устроен внутри. Читатель — разработчик.

---

## 0. Главный тезис

**Деньги считает арифметика, а не модель.** ИИ подбирает расценку и вытаскивает
факты из текста, но ни одного числа в смете не касается: все суммы считает
`EstimateCalculator` на `BigDecimal` по формулам СН-2012. Модель не может
«немного ошибиться» в цифре — у неё физически нет доступа к денежным колонкам.

Из этого следуют два свойства, которые видны по всему приложению:

- **у каждого числа есть происхождение** — периодичность помечена источником
  (`Midio` / `Паспорт, с. 14` / `ПКМ`), расценка помечена способом подбора
  (`LEARNED` / `CATALOG` / `AI_ETALON` / `AI`);
- **неуверенность видна, а не спрятана** — где нельзя выбрать однозначно,
  строка уходит «на проверку» инженеру. Так сделано в трёх местах: подбор
  расценки, сопоставление с Midio, сверка цитаты из паспорта.

## 1. Объекты, системы, документы

Объект → инженерные системы (АПС, СОУЭ, СКУД, вентиляция, ИТП…) → документы.

Конвейер обработки: загрузка (PDF / DOCX / XLSX / TXT / CSV / JPG / PNG) →
извлечение текста (PDFBox / POI / Tika) → если текстового слоя нет, OCR
(Tesseract, rus+eng, 300 dpi) → чанкинг → индексация. Всё асинхронно, статусы
видны в интерфейсе.

Поиск: PostgreSQL `tsvector` с русской конфигурацией + GIN-индекс, `pg_trgm`
для опечаток. Область — документ, объект или все объекты.

## 2. Чат по документации

Ответы со ссылкой на источник: файл + страница. Важная деталь: количественные
вопросы («сколько дымовых извещателей?») отвечаются **по структурированному
реестру оборудования**, а не по фрагментам PDF — считать позиции по тексту
значит получить неверное число.

Без настроенного ИИ чат работает в экстрактивном режиме: показывает релевантные
фрагменты с источниками.

## 3. Реестр оборудования: два уровня

- **Оборудование объекта** — что физически стоит на адресе.
- **Уникальное оборудование** — одна запись на модель, общая для всех объектов.
  К ней привязаны паспорт и плановые работы: загрузили один раз — работает
  везде, где модель встречается.

Ключ идентичности: `наименование | модель | производитель | система`.
Нормализация сводит регистр, ё→е, неразрывные пробелы и все виды дефисов к
общему виду. Система входит в ключ **намеренно**: один коммутатор в СКУД и в
видеонаблюдении — две записи с разными регламентами.

Наполнение: импорт Excel-спецификаций с детекцией дублей, извлечение из
PDF/сканов (vision-модель читает картинку страницы — точнее, чем OCR), ручной
ввод.

## 4. Откуда берётся регламент работ

Приоритет источников:

| Приоритет | Источник | Почему | Пометка в смете |
|---|---|---|---|
| 1 | **Midio** | регламент вела команда — принятое решение | `Midio` |
| 2 | **Паспорт** | извлечено ИИ, но с проверяемой цитатой | `Паспорт, с. 14` |
| 3 | **ПКМ** | типовой регламент по системе | `ПКМ: …` |
| 4 | **Название расценки** | «- ежемесячное» в наименовании | — |

Работы, заведённые вручную, остаются при любом источнике.

### Разбор паспорта — контроль галлюцинаций

Модель обязана привести **дословную цитату и номер страницы** для каждой
работы. Дальше цитата ищется в тексте паспорта:

- **нашли** → работа подтверждена, страница берётся из найденного места
  (не из ответа модели — она в этом ошибается);
- **не нашли** → работа сохраняется, но помечается «не подтверждена», и пометка
  доезжает до обоснования строки сметы.

Есть запасной поиск по словам (70 % совпадения в окне) — OCR путает буквы,
дословного вхождения может не быть. Скан не тупик: сначала локальный OCR,
без него — vision-модель постранично.

Модель разбора переключается в карточке оборудования (allowlist
`AI_PASSPORT_MODELS`). Молчание провайдера — это ошибка с причиной («кончился
лимит»), а не «в паспорте нет работ»; зависший разбор освобождается по
таймауту и при рестарте приложения.

## 5. Каталог расценок СН-2012

Сборники загружаются файлами и разбираются в таблицу: шифр, наименование,
единица, ЗП / ЭМ / ЗПМ / МР, трудозатраты, состав работ.

Парсер написан по граблям реальных сборников:

- шифры, разорванные переносом строки («22-2203-104-» / «11/1»);
- наименования, цитирующие **чужие** шифры (новая расценка начинается только с
  шифра в начале строки);
- строки, разрезанные разрывом страницы (разбор идёт по непрерывному тексту
  документа, а не постранично);
- смещённые колонки (берётся полный ряд из шести чисел; если в ряду нет ЗП —
  цены не угадываются: пустая цена честнее выдуманной).

**Самопроверка каталога**: разобранные расценки сверяются с 22 вручную
выверенными; расхождения показываются по конкретным полям.

## 6. Память решений и эталон

Таблица решений: `(уникальное оборудование, операция, система) → шифр расценки,
периодичность, обоснование`. Два способа наполнения:

- **загрузка эталонной сметы XLSX** — разделы файла распознаются как системы,
  решения сохраняются с источником `REFERENCE`;
- **кнопка «В эталон»** на смете — строки уходят в память как `APPROVED`.

То же оборудование на другом объекте получает расценку **детерминированно и
бесплатно**. ИИ нужен только для нового — память со временем вытесняет модель
из процесса.

## 7. Сборка сметы (reuse-first)

`EstimateDraftService`, для каждой позиции по порядку:

1. **память решений** → `LEARNED`;
2. **эталон по модели** → сравнение нормализованных моделей по Левенштейну
   (порог 0.75). Пример, почему одной похожести мало: «РМ-4К» одинаково близок
   к «РМ-1К» и «РМ-4» (одна правка символа), а расценки разные. При равной
   похожести побеждает совпадение **по числу в модели**; если и это не разводит
   варианты с разными расценками — решает инженер;
3. **каталог** → `CATALOG`;
4. **ИИ-подбор** из короткого RAG-списка найденных расценок → `AI`.

Неоднозначное помечается «⚠ НА ПРОВЕРКУ» с вариантами. Комплексные испытания
АПС зашиваются в каждую смету АПС отдельной строкой (количество пустое, если
не указана площадь объекта).

В редакторе: альтернативные расценки с ценами и составом работ для сравнения,
объединение одинаковых строк, ручной выбор из каталога — в том числе из другой
инженерной системы.

## 8. Расчёт

`EstimateCalculator` — чистая арифметика, два блока: уровень СН-2012 и пересчёт
в уровень РТ.

```text
L = K·J                       N = L/M
ЗП=O·N·S   ЭМ=P·N·S   ЗПМ=Q·N·S   МР=R·N
НР = ЗП·нрЗП + ЗПМ·нрЭМ       НП = ЗП·нпЗП + ЗПМ·нпЭМ
Итого = ЗП+ЭМ+МР+НР+НП        НДС = round(Итого·ставка, 2)
```

Нюансы, которые обычно спрашивают:

- НР и НП начисляются **на фонд оплаты труда** (ЗП рабочих + ЗПМ машинистов),
  а не на полную стоимость эксплуатации машин: в ЭМ входят амортизация, ГСМ и
  ремонт — не база для начислений;
- опорное тождество СН-2012: **прямые затраты = ЗП + ЭМ + МР** (ЗПМ входит в
  ЭМ, а не отдельное слагаемое) — по нему же проверяется каталог;
- округляется только НДС (до копеек), остальное — полная точность.

## 9. Экспорт XLSX

Не снимок чисел, а **живой документ**: формулы с абсолютными ссылками на лист
параметров, лист расценок, итоговый лист. Заказчик меняет коэффициент — всё
пересчитывается. Каждая выгрузка — новая версия (суффикс в имени + история
версий в файле).

## 10. Проверка сметы сильной моделью

Отдельный провайдер `AI_REVIEW_*`: задача — рассуждение по длинному контексту,
а не выбор из списка. Модель получает смету целиком + эталон + методику и
возвращает **только замечания** — смету не меняет.

- **Переключение модели в интерфейсе** из allowlist `AI_REVIEW_MODELS`
  (сравнение моделей на одной смете без пересборки контейнера; произвольное
  имя из браузера отклоняется — иначе можно было бы гонять любую модель за
  счёт владельца ключа).
- **Применение правок**: по одному замечанию и «применить всё». Поддержано
  `SET_RATE`, `SET_PERIODICITY`, `SET_QTY`, `SET_OPERATION_NAME`, `ADD_ROW`.
  Удаление строк модель предлагать не может — это решение инженера.
- **Показать в смете** — переход к строке с подсветкой.
- **Разбор замечания**: короткий приходит вместе с проверкой, глубокий — по
  кнопке, всегда моделью проверки.
- Результат **хранится рядом со сметой** (переживает перезагрузку страницы),
  повторный прогон предупреждает о затирании, удаление сметы уносит проверку
  каскадом.

## 11. Интеграция с Midio

Регламенты уже ведутся в Midio — разбирать те же паспорта второй раз незачем.

- Клиент к их execute-API: `POST /api/execute/{Domain.Method}`, общий конверт
  тела, Bearer из `Auth.Signin`, автоперелогин при протухшем токене.
  **Только чтение.**
- Сопоставление оборудования: идентификатор Midio (переживает переименования)
  → точный ключ реестра → похожесть модели с разведением по числам.
  Неоднозначное — на подтверждение инженеру; после подтверждения связь идёт по
  идентификатору. Отдельно — «нет в реестре» (лечится синхронизацией с
  объектами, а не выбором варианта).
- Повторный прогон заменяет только работы Midio; паспортные и ручные не
  трогает.
- Сохраняется `MANDATORY` / `RECOMMENDED` — различие денежное: рекомендуемые
  работы заказчик оплачивать не обязан.
- Наименование и модель в Midio упакованы в одно поле через `..`
  («Извещатель..ИП 212-64-R3») — распаковываются. Периодичность берётся
  числом из `recurrenceInterval` + `recurrenceIntervalUnit`, а не разбором
  текста: «раз в 2 года» через строку потерялось бы.

Статус: код написан по документации API и покрыт тестами (маппинг, матчер,
синхронизация); живой прогон против стенда ещё не выполнялся — из среды
разработки сеть на midio.ru закрыта. Первый запуск — по кнопке
«Синхронизировать с Midio» с реальными кредами в `.env`.

## 12. Провайдеры ИИ — пять слотов

У задач разная цена и разные требования к модели, поэтому слоты независимые:

| Слот | Задача | Класс модели |
|---|---|---|
| `AI_*` | чат по документации | локальная или облачная |
| `AI_VISION_*` | извлечение со сканов по картинке | vision |
| `AI_MATCH_*` | подбор расценок из короткого списка | дешёвая |
| `AI_PASSPORT_MODEL` | разбор паспортов (через match-провайдер) | дешёвая |
| `AI_REVIEW_*` | проверка готовой сметы | сильная |

Экономика: дорогая модель используется только там, где нужно рассуждение
(проверка сметы). Подбор расценок и паспорта — копеечные задачи на коротком
контексте. Память решений делает повторные подборы вовсе бесплатными.

## 13. Стек и инфраструктура

```text
Backend     Java 21, Spring Boot 3.3, Spring Security (JWT), Spring Data JPA, Liquibase
Frontend    React 18, TypeScript, Vite, Tailwind CSS
БД          PostgreSQL 16 (tsvector russian + GIN, pg_trgm), 21 миграция Liquibase
Файлы       MinIO или локальная папка
Документы   PDFBox 3, POI 5.3, Tika 2.9; OCR — Tesseract CLI
ИИ          любой OpenAI-совместимый API (по умолчанию локальный Ollama)
Деплой      Docker Compose (postgres, minio, ollama, backend, frontend)
Тесты       40 классов: юнит + @SpringBootTest на PostgreSQL
```

## 14. Что честно сказать про незаконченное

- Интеграция с Midio не гонялась против живого стенда (сетевые ограничения
  среды разработки) — код и тесты готовы, нужен первый запуск с кредами.
- Поиск расценки по шифру идёт по всем сборникам сразу — при загрузке второго
  уровня цен станет неоднозначным. Известно, в плане (уровни цен +
  переиндексация).
- Следующие по плану: полная арифметическая проверка каталога по тождеству
  «прямые = ЗП + ЭМ + МР» и детерминированный линтер сметы до обращения к
  модели.
