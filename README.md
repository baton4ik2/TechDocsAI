# TechDocs AI

База инженерной документации по объектам и сборщик смет технического
обслуживания по **СН-2012**.

Две связанные задачи. Первая — хранить документацию (паспорта, проектную и
исполнительную документацию, спецификации, схемы) с поиском и вопросами на
обычном языке. Вторая, ради которой всё и затевалось, — **собрать годовую смету
обслуживания объекта**: взять реестр оборудования, определить регламент работ,
подобрать расценки СН-2012, посчитать деньги и выгрузить XLSX, который не
стыдно отдать заказчику.

---

## Принцип: где ИИ, а где его нет

Это главное архитектурное решение проекта, поэтому оно первым.

**Деньги считает арифметика, а не модель.** ИИ не участвует ни в одном
вычислении: он подбирает расценку и вытаскивает факты из текста, но все суммы
считает `EstimateCalculator` по формулам СН-2012 на `BigDecimal`. Модель не
может «немного ошибиться» в цифре — она физически не касается денежных колонок.

**У каждого числа в смете есть происхождение.** Периодичность приходит из
источника с пометкой: `Midio` / `Паспорт, с. 14` / `ПКМ` / из наименования
расценки. Расценка — с пометкой `LEARNED` (память решений), `CATALOG`,
`AI_ETALON`, `AI`. Инженер видит, откуда взялась строка, и может это проверить.

**Неуверенность видна, а не спрятана.** Если выбрать нельзя однозначно — строка
помечается «на проверку» и решает человек. Так сделано в трёх местах: подбор
расценки по эталону, сопоставление оборудования с Midio, сверка цитаты из
паспорта.

## Разделы приложения

### 1. Объекты, системы, документы

Объект → инженерные системы (АПС, СОУЭ, СКУД, вентиляция, ИТП…) → документы.

Загрузка PDF / DOCX / XLSX / TXT / CSV / JPG / PNG. Обработка асинхронная
(`documentProcessingExecutor`): извлечение текста (PDFBox / POI / Tika),
разбиение на фрагменты, индексация. Если текстового слоя нет — документ
распознаётся **OCR** (Tesseract, `rus+eng`, 300 dpi).

Поиск — PostgreSQL `tsvector` с русской конфигурацией + GIN, плюс `pg_trgm` для
опечаток. Область поиска: один документ, один объект или все объекты.

### 2. Чат по документации

Ответ с указанием источника — файл и страница. Количественные вопросы
(«сколько дымовых извещателей?») отвечаются **по структурированному реестру
оборудования**, а не по случайно найденным фрагментам PDF: считать позиции по
тексту — верный способ получить неверное число.

Без ИИ чат продолжает работать в экстрактивном режиме — показывает релевантные
фрагменты с источниками.

### 3. Реестр оборудования

Два уровня:

- **оборудование объекта** — что физически стоит на конкретном адресе;
- **уникальное оборудование** — одна запись на модель, общая для всех объектов.
  К ней привязаны паспорт и плановые работы: загрузили один раз — работает
  везде, где эта модель встречается.

Ключ идентичности: `наименование | модель | производитель | система`.
Нормализация сводит регистр, `ё→е`, неразрывные пробелы и все виды дефисов
(`–—‑−`) к общему виду. **Система входит в ключ намеренно**: один и тот же
коммутатор в СКУД и в видеонаблюдении — две разные записи с разными
регламентами.

Наполнение: импорт из Excel-спецификаций с детекцией дублей, извлечение из PDF
(в т.ч. vision-моделью по картинке страницы — на сканах это заметно точнее
OCR), ручной ввод.

### 4. Откуда берётся регламент работ

Приоритет источников, сверху вниз:

| Источник | Что это | Пометка в смете |
|---|---|---|
| **Midio** | регламент, заведённый командой в Midio | `Midio` |
| **Паспорт** | работы, извлечённые ИИ из паспорта | `Паспорт, с. 14` |
| **ПКМ** | регламент по типу системы | `ПКМ: …` |
| **Наименование расценки** | «- ежемесячное» в названии | — |

Midio старше паспорта: там регламент вела команда, это принятое инженерное
решение, а не извлечение ИИ из текста. Работы, заведённые вручную, остаются при
любом источнике.

#### Разбор паспорта

Модель обязана привести **дословную цитату и страницу**. Цитата ищется в тексте
паспорта: нашли — работа подтверждена, и страница берётся из найденного места,
а не из ответа модели; не нашли — работа сохраняется, но помечается «не
подтверждена», и та же пометка уходит в обоснование строки сметы. Есть запасной
поиск по словам — OCR путает буквы, дословного вхождения может не быть.

Скан не тупик: сначала локальный OCR (бесплатно и даёт текст для сверки цитат),
если его нет — vision-модель по картинкам страниц, где номер страницы известен
точно.

Модель разбора переключается прямо в карточке оборудования из списка
`AI_PASSPORT_MODELS` — паспорта разной сложности, и на трудных дешёвая модель
пропускает работы.

### 5. Каталог расценок СН-2012

Сборники загружаются файлами и разбираются в таблицу расценок: шифр,
наименование, единица измерения, ЗП / ЭМ / ЗПМ / МР, трудозатраты, состав работ.

Парсер написан по граблям реальных сборников: шифры, разорванные переносом
строки; наименования расценок, которые цитируют **другие** шифры; строки,
разрезанные разрывом страницы; смещённые колонки стоимостей. Если в найденном
ряду чисел нет ЗП — цены не угадываются, строка пропускается: пустая цена
честнее выдуманной.

**Самопроверка каталога** (`NormativeVerificationService`) сверяет разобранные
расценки с 22 вручную выверенными эталонными и показывает расхождения по
конкретным полям.

### 6. Память решений и эталон

Таблица «решений»: `(уникальное оборудование, операция, система) → шифр
расценки, периодичность, обоснование`.

Наполняется двумя способами:

- **загрузка эталонной сметы XLSX** — готовая смета разбирается по разделам
  (разделы = инженерные системы), решения сохраняются с источником `REFERENCE`;
- **кнопка «В эталон»** на смете — строки уходят в память с источником
  `APPROVED`.

Дальше то же оборудование на другом объекте получает расценку **детерминированно
и бесплатно**, без обращения к ИИ. ИИ нужен только для нового.

### 7. Сборка сметы

`EstimateDraftService`, порядок для каждой позиции:

1. **память решений** → готовое решение (`LEARNED`);
2. **эталон по модели** — сравнение нормализованных моделей по Левенштейну
   (порог 0.75) с разведением по числам: «РМ-4К» одинаково близок к «РМ-1К» и
   «РМ-4», а расценки у них разные, поэтому при равной похожести побеждает
   совпадение по номеру;
3. **поиск по каталогу** (`CATALOG`);
4. **ИИ-подбор** из короткого RAG-списка найденных расценок (`AI`).

Неоднозначные случаи не додумываются: строка получает пометку «⚠ НА ПРОВЕРКУ» с
вариантами, выбирает инженер. Комплексные испытания АПС зашиты в каждую смету
отдельной строкой.

В редакторе: подбор альтернативной расценки с ценами и составом работ для
сравнения, объединение одинаковых строк, ручной выбор расценки из каталога — в
том числе из другой инженерной системы.

### 8. Расчёт

`EstimateCalculator` — чистая арифметика на `BigDecimal`, два блока: уровень
СН-2012 и пересчёт в уровень РТ.

```text
L = K·J                       N = L/M
ЗП=O·N·S   ЭМ=P·N·S   ЗПМ=Q·N·S   МР=R·N
НР = ЗП·нрЗП + ЗПМ·нрЭМ       НП = ЗП·нпЗП + ЗПМ·нпЭМ
Итого = ЗП+ЭМ+МР+НР+НП        НДС = round(Итого·ставка, 2)
```

Накладные и плановые начисляются **на фонд оплаты труда** (ЗП рабочих и ЗПМ), а
не на полную стоимость эксплуатации машин: в ЭМ входят амортизация, ГСМ и
ремонт — они не база для начислений. Округляется только НДС, до копеек;
остальное считается в полной точности.

Опорное тождество СН-2012, по которому проверяется каталог:
**прямые затраты = ЗП + ЭМ + МР** (ЗПМ входит в ЭМ, а не отдельное слагаемое).

### 9. Экспорт XLSX

Выгрузка — не «снимок чисел», а **живой документ**: формулы со ссылками на лист
параметров, лист расценок, итоговый лист. Заказчик может поменять коэффициент и
увидеть пересчёт.

Каждая выгрузка — новая версия: суффикс в имени файла и запись в истории версий.

### 10. Проверка сметы сильной моделью

Отдельный провайдер (`AI_REVIEW_*`), потому что задача другая — рассуждение по
длинному контексту, а не выбор из короткого списка. Модель получает смету
целиком вместе с эталоном и методикой и возвращает **только замечания**: смету
она не меняет.

Возможности:

- **переключение модели прямо в интерфейсе** из списка `AI_REVIEW_MODELS` —
  чтобы сравнивать модели на одной смете, не пересобирая контейнер. Запрос
  принимается только с моделью из списка: произвольное название из браузера
  означало бы обращение к чему угодно за счёт владельца ключа;
- **применение правки** по каждому замечанию и «применить всё». Поддержаны
  `SET_RATE`, `SET_PERIODICITY`, `SET_QTY`, `SET_OPERATION_NAME`, `ADD_ROW`.
  Удаление строк модель предлагать не может — это решение инженера;
- **показать в смете** — переход к строке с подсветкой;
- **разбор замечания**: короткий приходит вместе с проверкой, глубокий — по
  кнопке и всегда моделью проверки;
- результат **хранится рядом со сметой**: обновление страницы его не теряет,
  повторный прогон предупреждает о затирании.

### 11. Интеграция с Midio

Регламенты обслуживания уже ведутся в Midio — разбирать те же паспорта руками
второй раз незачем.

Клиент ходит в их execute-API (`POST /api/execute/{Domain.Method}`, Bearer из
`Auth.Signin`) и читает оборудование, планы обслуживания и типы плановых работ.
**Только чтение**: в Midio ничего не создаётся и не удаляется.

Сопоставление оборудования: связь по идентификатору Midio (переживает
переименования на той стороне) → точный ключ реестра → похожесть модели.
Неоднозначное **не привязывается молча** — возвращается списком с кандидатами,
инженер подтверждает, дальше синхронизация идёт по идентификатору. Отдельно
показывается оборудование, которого нет в реестре вовсе: это лечится не выбором
варианта, а синхронизацией реестра с объектами.

Повторный прогон заменяет только работы Midio — паспортные и ручные не трогает.
Сохраняется признак `MANDATORY` / `RECOMMENDED`: различие денежное,
рекомендуемые работы заказчик оплачивать не обязан.

### 12. Google Drive (необязательно)

Синхронизация папки Drive с документами объекта через **сервисный аккаунт** (без
OAuth-модерации Google). Подпапки = инженерные системы. Изменённые файлы
скачиваются и обрабатываются, неизменившиеся пропускаются.

## Стек

```text
Backend     Java 21, Spring Boot 3.3, Spring Security (JWT), Spring Data JPA, Liquibase
Frontend    React 18, TypeScript, Vite, Tailwind CSS
БД          PostgreSQL 16 (tsvector russian + GIN, pg_trgm)
Файлы       MinIO (или локальная папка: techdocs.storage.type=file)
Документы   Apache PDFBox 3, Apache POI 5.3 (XSSF/XWPF), Apache Tika 2.9
OCR         Tesseract CLI (rus+eng)
ИИ          любой OpenAI-совместимый API
Деплой      Docker Compose
```

### Пакеты бэкенда

```text
object, engineeringsystem   объекты и инженерные системы
document, processing        загрузка, извлечение текста, OCR, чанкинг
search, chat                полнотекстовый поиск и вопросы по документации
equipment                   оборудование объектов, импорт из Excel
uniqueequipment             реестр моделей, паспорта, плановые работы
normative                   каталог СН-2012: разбор сборников, самопроверка
pkm                         регламенты по типам систем
estimate                    сметы: черновик, расчёт, память решений, экспорт, ИИ-проверка
midio                       интеграция с Midio
integration                 Google Drive
ai                          клиент OpenAI-совместимых API (5 слотов провайдеров)
```

### Провайдеры ИИ

Пять независимых слотов — у задач разная цена и разные требования к модели:

| Слот | Задача | Типичная модель |
|---|---|---|
| `AI_*` | чат по документации | локальная или облачная |
| `AI_VISION_*` | извлечение со сканов по картинке | vision-модель |
| `AI_MATCH_*` | подбор расценок из короткого списка | дешёвая |
| `AI_PASSPORT_MODEL` | разбор паспортов (через match-провайдер) | дешёвая |
| `AI_REVIEW_*` | проверка готовой сметы | сильная |

## Быстрый старт

```bash
cp .env.example .env
docker compose up --build
```

http://localhost:3000, вход `admin@techdocs.local` / `admin123`.

По умолчанию ИИ — **локальный Ollama** в составе compose: бесплатно, без ключей,
документы не покидают сервер. Модель `qwen2.5:7b` (~4.7 ГБ) скачивается при
первом запуске (`docker compose logs -f ollama-init`), нужно ~8 ГБ RAM.

Альтернативы — в `.env.example`: OpenAI, любой OpenAI-совместимый шлюз, либо
работа вовсе без ИИ (чат в экстрактивном режиме, расценки — по каталогу и
памяти решений).

Интеграция с Midio включается тремя переменными:

```bash
MIDIO_BASE_URL=https://midio.ru
MIDIO_LOGIN=<сервисная учётная запись>
MIDIO_PASSWORD=<её пароль>
```

Заводите **отдельную сервисную учётную запись**, а не личную: у API есть методы
удаления оборудования и планов.

## Тесты

40 тестовых классов. Юнит-тесты (парсеры сборников, расчёт сметы, периодичность,
сопоставление моделей, разбор паспорта, маппинг Midio, JWT, чанкер) не требуют
инфраструктуры. Интеграционные (`@SpringBootTest`) поднимают полный контекст и
работают с PostgreSQL:

```bash
createdb techdocs_test          # владелец — пользователь techdocs
cd backend && mvn test
```

Параметры БД переопределяются через `TEST_DB_URL`, `TEST_DB_USERNAME`,
`TEST_DB_PASSWORD`. Сборка образа идёт с `-DskipTests`.

## Разработка без Docker

```bash
cd backend && mvn spring-boot:run     # нужны PostgreSQL и MinIO
cd frontend && npm install && npm run dev
```
